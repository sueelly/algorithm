# 4949 균형잡힌 세상 - 코드 리뷰

## 📝 내 코드 분석

### 접근 방식
- **스택**을 이용한 괄호 짝 검사. `char[] stack`으로 직접 스택을 구현했고, `index`로 top 위치를 관리.
- 여는 괄호 `(`, `[`는 `stack[index++] = c`로 push, 닫는 괄호 `)`, `]`는 `index == 0`이거나 `stack[--index]`와 짝이 맞지 않으면 `"no"` 반환. 마지막에 `index != 0`이면 열린 괄호가 남은 것이므로 `"no"`.

### 시간 복잡도
- **O(n)** — `line` 길이 n만큼 한 번 순회. 각 문자는 최대 1번 push 또는 1번 pop.

### 공간 복잡도
- **O(n)** — 최악의 경우 괄호만 연속으로 들어오면 `stack`에 n개 저장. `line.toCharArray()`로 인한 n 크기 배열도 있지만, 스택 자체가 O(n)이므로 전체 O(n).

### 장점
- `Stack` 클래스 대신 **배열 스택**을 써서 객체 생성·오토박싱 없이 동작해 메모리·속도 측면에서 유리함.
- 조건 분기가 단순하고, `index` 하나로 push/pop을 처리해 코드가 짧고 읽기 쉬움.
- 괄호가 아닌 문자는 그대로 두고 스택 연산만 하므로 로직이 명확함.

### 개선 가능한 점
- `toCharArray()`는 매 호출마다 길이 n인 새 배열을 만들므로, 긴 줄이 많으면 `charAt(i)`로 한 번씩 순회하는 편이 공간을 아낄 수 있음.
- 스택 크기를 `line.length()`로 잡고 있는데, 괄호만 저장하므로 “괄호 개수 상한”으로 줄이면 이론상 메모리를 더 줄일 수 있음(다만 최악은 여전히 O(n)).

## 🏆 대표 풀이

### 접근 방식
- `java.util.Stack<Character>`를 사용해 여는 괄호는 `push`, 닫는 괄호는 `empty()` / `peek()` 확인 후 `pop`. 한 번에 `"no"`로 끝내기 위해 `boolean valid`로 플래그를 두고, 끝에 `valid && stack.empty()`로 `"yes"`/`"no"` 출력.

### 코드
```java
Stack<Character> stack = new Stack<>();
boolean valid = true;

for (int i = 0; i < s.length(); i++) {
    char c = s.charAt(i);
    if (c == '(' || c == '[') {
        stack.push(c);
    } else if (c == ')') {
        if (stack.empty() || stack.peek() != '(') {
            valid = false;
            break;
        }
        stack.pop();
    } else if (c == ']') {
        if (stack.empty() || stack.peek() != '[') {
            valid = false;
            break;
        }
        stack.pop();
    }
}
System.out.println(valid && stack.empty() ? "yes" : "no");
```

### 내 코드와의 차이점
| 구분 | 내 코드 | 대표 풀이 |
|------|--------|-----------|
| 스택 구현 | `char[]` + `index` (배열 스택) | `Stack<Character>` |
| 메모리/속도 | 배열만 사용, 오버헤드 적음 | `Character` 오토박싱, 노드 오버헤드 |
| 흐름 제어 | 조건 만족 안 되면 즉시 `return "no"` | `valid` 플래그 + 마지막에 한 번 판정 |
| 입력 순회 | `for (char c : line.toCharArray())` | `s.charAt(i)` |

- **정답 여부**: 둘 다 스택 LIFO로 짝을 검사하므로 논리는 동일하고, 둘 다 올바른 풀이.
- **효율성**: 채점 환경에서는 내 코드처럼 배열 스택 + 즉시 return이 보통 더 빠르고 메모리도 적게 씀.
- **가독성**: `Stack`을 쓰면 “스택” 의도가 더 드러나서 교육/공유용으로는 좋고, 배열 스택은 구현이 짧고 성능에 유리함.

## 🎯 다음에 시도해볼 것

### 이 문제에서 배울 점
- 괄호 짝 맞추기는 **LIFO**가 필요하므로 스택이 자연스러운 선택이다.
- 스택을 `Stack` 클래스 대신 배열+인덱스로 구현하면 성능·메모리를 조금이라도 줄일 수 있다.

### 보완할 점
- 다른 문제에서 “스택으로 풀 수 있는지”만 빠르게 떠올릴 수 있으면, 비슷한 괄호/중첩 구조 문제는 같은 패턴으로 확장할 수 있다.

### 관련 문제 추천
- **9012번** 괄호 (소괄호만)
- **10799번** 쇠막대기 (괄호 + 개수 세기)
- **2504번** 괄호의 값 (괄호 짝에 따른 수식 계산)

### 도전 과제
- `toCharArray()` 없이 `charAt(i)`만으로 한 번 순회해 동일 로직 구현해 보기.
- 괄호 종류가 `()`, `[]`, `{}` 세 가지로 늘어난다면 조건만 확장해서 같은 방식으로 풀 수 있는지 확인해 보기.
